SCORE_AGREE: yes

SUMMARY:
The failure handling is good and the failure *noticing* is close to nonexistent, which averages out to a 5. On the resilience side: 13 loaders wrap their database calls in ssrBudget (src/lib/ssrBudget.ts), so a dead backend gives an empty grid in 5 seconds instead of a hanging tab; src/server.ts catches the 500 that h3 turns into a JSON blob and swaps in a real HTML error page; six routes have their own error and not-found components; and the status writes in src/hooks/useUserStatus.ts fall back from upsert to manual replace to a local outbox before giving up. On the observability side: there is no Sentry, no error tracker of any kind in package.json, and the only reporting path (src/lib/lovable-error-reporting.ts line 23) calls window.__lovableEvents?.captureException?.() through two optional chains on a global that nothing in this repo ever defines, so in production every caught error goes to console.error and dies there. The concrete cost showed up while I was looking: the person-index refresh job has failed 3 of its last 12 nightly runs on statement timeout, most recently this morning at 09:32 UTC, and its runtime has climbed from 25 seconds on 16 Aug to 117 seconds on 26 Aug against a 120-second ceiling, so it will now fail most nights. Nothing anywhere reports that. Separately, today's catalog sync never ran at all: GitHub Actions shows the last daily-catalog-sync run on 26 Aug, and the database has 0 media rows updated today against 6,331 yesterday, 4.5 hours past the 08:00 UTC schedule.

STRENGTHS:
- Every SSR loader that touches the database is time-boxed. ssrBudget resolves undefined after 5 seconds and never rejects, so a Supabase outage degrades to an empty page that React Query heals on the client. 13 call sites across the route files. The comment cites the 2026-07-02 incident that caused it, which is the right way to keep a guard from being deleted later.
- src/server.ts handles the failure mode a plain try/catch misses: h3 swallows in-handler throws into a 500 JSON body, so the code sniffs for {"unhandled":true,"message":"HTTPError"}, recovers the real stack out-of-band via src/lib/error-capture.ts, and returns a styled HTML page instead of raw JSON.
- The root error component deliberately does not render error.message, with a comment saying why (it can leak schema, API paths, env var names). That is a real decision, not an oversight.
- The nightly catalog sync workflow has a freshness canary that fails the run red if the newest media.updated_at is over 48 hours old, written after upserts failed silently for five weeks in Jul-Aug. Retries are limited to 502/503/504/429/000, the backfill has a 1,200-second wall-clock budget after an unbounded run took the database down, and every pass is resumable.
- Movie Night writes are wrapped in a single `write` helper (src/routes/night.$code.tsx around line 160) that toasts "That did not save. Check your connection." and re-syncs on failure, and the state fetch distinguishes not_found from not_member instead of spinning forever.

GAPS:
- No error telemetry reaches the owner from production. Nothing in package.json does error tracking; reportLovableError depends on a global the Lovable preview harness injects and this repo never defines. PostHog only loads after "all" cookie consent (src/components/balasaur/AnalyticsManager.tsx) and captures no exceptions. A user hitting the 500 page is invisible.
- Database cron failures are silent. person-index-refresh failed on 23, 24 and 27 Aug with "canceling statement due to statement timeout" and its runtime is trending straight into the ceiling. Person pages have been serving a stale materialized view on those days. There is no alert, no failure row, no dashboard: I found it only by reading cron.job_run_details directly.
- The freshness canary only runs *inside* a workflow run, so a run that never starts is undetectable by it. That is exactly what happened today: no daily-catalog-sync run for 27 Aug exists, and zero media rows have been written. The catalog will have to be two days stale before anything turns red, and even then the signal is a GitHub email.
- gsc_sync_log records dispatch and never outcome. All 7 rows have ok = null and detail text like "dispatched sync 106, totals 107". A log column that is null in 100% of rows is not a log.
- Movie Night has no server-side record of why a room stalls. 12 of 13 rooms are still in lobby with 1 member and 0 rolls; the roll RPC returns {error} strings the client shows as a toast and then discards, so the only evidence of a broken roll is a room that sits there. For a feature shipped 24 hours ago with no traffic, that is the one place a log line would have paid for itself.
- One Movie Night write escapes the safe wrapper: src/routes/night.$code.tsx line 156 does `void saveNightPrefs(...).then(...)` with no catch, so if the history submission rejects it is an unhandled rejection and the recommender silently never learns what the visitor has seen. Every other call on that page goes through `write`.
