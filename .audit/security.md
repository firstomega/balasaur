SCORE_AGREE: yes

SUMMARY:
The foundations are solid and one specific hole is not. Row level security is enabled on all 25 tables in the public schema, and the tables holding personal data carry real owner-scoped policies: profiles, saved_filters and user_media_status have 4 policies each, all keyed on auth.uid(). No secret reaches the browser. TMDB and OMDb keys are read only from process.env inside server-only files (src/lib/media.server.ts lines 1335 to 1336), and the one JWT committed to the repo, at supabase/migrations/20260821143000_gsc_nightly_sync.sql line 40, decodes to "role":"anon", which is public by design. The hole is that two internal maintenance functions, rebuild_collections() and refresh_catalog_facets_cache(), are SECURITY DEFINER and executable by the anon role, so anyone holding the publishable key that ships in every page can POST to /rest/v1/rpc/rebuild_collections. That call is not cheap: the nightly cron run of the same function took 38.3 to 44.3 seconds on each of the last four nights and rewrites 678 collections and 31,055 collection_items rows. Nobody granted that access; Postgres hands every new function EXECUTE to PUBLIC unless you revoke it, and the night_* functions got explicit grants (movie_night_backbone.sql lines 558 to 564) while these two got the default and were never revoked.

STRENGTHS:
- RLS is genuinely on, not decorative. All 25 public tables have relrowsecurity = true, and the four tables with user data (profiles, saved_filters, user_media_status, plus collections) enforce ownership through auth.uid() rather than trusting a client-supplied user id.
- No credential leaks to the client. The service role key appears nowhere in .env and is read only in src/integrations/supabase/client.server.ts line 16 from the deploy environment. Searching every tracked file for JWT-shaped strings turned up exactly one, and it is the anon key, correctly labelled as public in a comment at the call site.
- The Movie Night token model is the right design. night_rooms, night_members and night_rolls have RLS on with zero policies and no anon table grants, so browsers cannot touch them at all; every operation goes through a definer function that requires the member_token uuid handed out at join time. The room code lets you join, the token lets you write. That separation is correct and it is documented in the migration header rather than left implicit.
- The public score endpoint is hardened rather than trusted. src/routes/api/public/v1/score.ts line 34 validates the id against /^(movie|tv)-\d{1,10}$/ before it reaches the database, returns six fixed columns, and suppresses rows flagged sensitive, so the service-role client behind it cannot be steered.
- Supabase's own security advisor is clean of anything ERROR level. Everything it reports is WARN or INFO, and the INFO items are the deliberate no-policy lockdown tables, not oversights.

GAPS:
- Two maintenance RPCs are open to the internet. rebuild_collections() and refresh_catalog_facets_cache() run as owner and accept calls from anon. One request burns roughly 40 seconds of database time and rewrites the tables every collection page reads; a handful of concurrent requests would take the site down and there is no rate limit or auth in front of them. This is the one item worth fixing this week, and the fix is two REVOKE statements.
- Anon and authenticated hold INSERT, UPDATE, DELETE and TRUNCATE on 16 tables including media, collections and media_cache. RLS blocks the row-level writes today, so this is latent rather than live, and TRUNCATE is not reachable because PostgREST does not expose it and the anon role is NOLOGIN. It is still a grant nobody intended, and it means RLS is the only thing standing between a stray policy edit and a wiped catalog.
- .env is tracked in git and matched by no rule in .gitignore. Its current contents are publishable keys only and a comment explicitly warns against putting the service role key there, so nothing is leaked now. The risk is mechanical: the file is one careless paste away from committing a real secret, and the comment is the only guard.
- night_create() has no per-caller limit. Its only brake is a global cap of 10,000 live rooms (movie_night_backbone.sql). A script can create 10,000 rooms in minutes and every real visitor then gets "at_capacity" until the 24-hour expiry drains it. 13 rooms exist today, so this costs nothing now, but the feature has no floor under it.
- Six functions run with a mutable search_path, including search_titles and slugify, both reachable from the browse surface. Every SECURITY DEFINER function correctly pins search_path, so this is not currently exploitable, but it is the same class of oversight as the two open RPCs: the default was accepted rather than chosen.
- Leaked password protection is off in Supabase Auth. Low stakes while sign-in is optional and the user count is small, but it is a one-toggle fix that should happen before accounts matter.

METHOD:
I queried the live project for table grants, pg_policies, RLS flags, SECURITY DEFINER functions with their EXECUTE grants and search_path settings, the pg_cron schedule, and the last four runtimes of the rebuild-collections job, then ran Supabase's security advisor; on the repo side I read the Supabase client files, the three /api/public routes, the Movie Night migrations, and grepped all tracked files and .env history for secrets. I could not test any of this end to end: this container has no outbound network, so I did not confirm by actually calling /rest/v1/rpc/rebuild_collections, and the reachability claim rests on the grant plus Supabase's own advisor naming that exact URL.
